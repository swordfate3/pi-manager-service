# 工作台目录浏览与终端会话统一登记

## 用户批准的范围

目录支持文件夹／文件名搜索和排序，电脑终端启动的普通 `pirun` 也应显示在同一个
Hub。用户明确不需要旧容器兼容，旧会话由用户退出后重开；不迁移或接管存活容器。
开发分支为 `codex/workbench-browser-terminal-sessions`，基线为 `abf550d`。

## 改动

- 当前目录名称子串匹配，忽略大小写，支持中文和 Unicode 规范化；不递归、不读取内容。
- 名称正序／倒序、最近／最早修改四种排序，文件夹始终在前。先匹配和排序，后每页200项。
- 显示总数、分页、清除、加载／空结果／失败重试；搜索输入250毫秒防抖，立即废弃旧请求。
- 文件仅展示名称和类型，不能作为启动目录；过滤、排序、翻页不改变已选工作区。
- 服务端保留工作区校验、私有路径保护、禁止符号链接和控制字符，单层扫描上限20,000项。
- 工作台从同一个内层Hub读取有效登记，只返回标签、会话名称、generation、相对入口和时间。
- 网页实例和终端登记按相对会话路径去重。终端卡片只能打开，不取得工作台停止／接管权限。
- 部署适配器 `pi-stack-deployment/scripts/pi-pirun` 读取安装目录下工作台私有配置，
  从 `stateRoot`／`hubCli` 推导原生签发、登记和回收路径；显式覆盖优先。
  已安装工作台不可用时不误连旧18300Hub，`on`拒绝启动、`auto`警告后不登记。
- 不改Pi镜像、共享卷、模型、扩展安装、工作区挂载、QQ截图、SSH/HF、隧道或阿里云配置。

## 异常退出卡片残留修复

用户随后报告异常结束后卡片仍在。只读核对发现两条`failed`记录对应的Docker
容器已经不存在。根因是轮询跳过`failed`，前端只过滤`stopped`，导致永久残留。

- 核对`failed`、`unknown`、`ready`，每实例约2秒一次；原容器已退出或不存在时
  收敛为`stopped`，保留数据库行、原请求身份、项目和Pi历史。
- Docker断连、无权限、畸形响应或已绑定ID不一致均保留`unknown`，不伪造已停止。
- 核对失败后阻止陈旧登记在两次探测之间恢复`ready`；确认恢复后才允许进入。
- 活启动器尚无首个Docker身份时，提前出现的登记不造成误移除或提前导航；
  已绑定身份的容器消失，即使启动器仍活着，也正常停止显示。
- 20项隔离生命周期回归；真实临时服务浏览器检查失败启动被确认清理、
  待处理请求解除、不自动重建以及不泄露启动器原始输出。
- 新增启动竞争测试先在旧判断下断言失败（`stopped`≠`unknown`），修复后通过。
  早先受限环境中的测试进程退出不作为断言失败证据。
- 独立审查补充发现：首轮异步inspect未完成时，同步列表曾可看到提前发布的
  `ready`。新增持有探测响应的确定性测试先RED；就绪发布现在要求已核实Docker ID，
  `starting`也参与探测，完成后才允许导航。
- 实际部署还发现本机Docker返回小写`error: no such object: <name>`，旧的大小写
  敏感判断误报未知。新增CLI格式测试先RED，改为忽略大小写且精确匹配本实例ID；
  其他对象不存在、socket文件不存在与daemon断连均不作为停止依据。
