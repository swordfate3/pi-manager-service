## 要证明什么

| 场景 | 正向对照 | 必须拒绝 |
| --- | --- | --- |
| Agent 提交 | 可提交和查询测试任务 | 直接批准、直接执行、附加 shell/执行参数 |
| 公共入口 | 可转交允许请求及冻结引用 | 读取审批凭据、修改策略/权威状态、控制 Docker |
| 执行器 | 唯一 TaskStore 写入者；核对精确批准 | 未批准、旧修订或变更内容的引用 |
| 文件隔离 | Agent 可写自己的新测试目录 | 读取/改写管理私有文件、修改执行器代码 |
| 生命周期 | 入口/Agent 退出不删除持久任务 | 终态重放；将新执行器误认成旧进程控制者 |

实验中的动作仅写固定测试标记。真实任务存储可以参与实验，但测试协议和标记动作不等于生产执行器。完整创建 Pi、Web 登记、聊天、停止、管理页面、MCP 与更新能力均不在本次通过声明之内。

### 故意开放边界的反向对照

在上述命令末尾增加 `--unsafe-fixture-admin-access --acknowledge-negative-control`；两个确认参数缺一不可。只向本次新建 Agent（UID 21004）增加本次管理员 socket 卷及 GID 21005，不修改其他角色或任何现有容器。

最终反向运行标识：`0797de2ea1d028875ef07ac98be65062`；**按预期退出 1**，准确报出 `BOUNDARY BREACH: connect /admin/approval.sock; operation succeeded`。这不是普通流程失败，也不把任何非零退出都算成功。完整原始日志为 `docker-negative-final.log`。该轮自身的清理通过、原有 16 个容器的 ID/启动时间相同，日志保留了失败位置。

控制器另外解析了正反两份日志：正常运行无 FAIL 且有最终通过标记；反向运行含精确越权错误、不含最终通过标记；二者均有清理通过标记与相等的前后快照。

### 发现并修复的测试环境问题

第一轮 `docker-safe.log` 在预检容器启动时报错：local 日志驱动默认压缩不兼容 `max-file=1`。未进入权限验证；临时资源已清理。随后加入并实际观察失败的回归测试，再显式配置 `compress=false`；没有更改守护进程配置。修复后的首次流程记录在 `docker-safe-attempt2.log`。

首次成功流程只检查了前端客户端，控制器额外要求测试真实公共入口进程，以及绕过入口直接请求执行器。最终正向日志已覆盖这些检查，不能以较早的一次成功替代最终覆盖。

## 仍然不能由本实验推断的事

- 夹具的审批能力只在内存保存；排队但尚未执行的任务重启后失败关闭，不能称为生产审批恢复完成。
- 共享公共 socket 不验证 requester 字符串或做多租户查询过滤；没有 HTTP 登录、Host/Origin、MCP、浏览器或跨机器授权验收。
- 没有运行真正 Pi、导入会话、接通 Web 登记、执行更新/回退，或为同宿主 UID 的原生 Agent 提供隔离。
- 没有处理容器逃逸、宿主/Docker 守护进程失陷；无法保证 SIGKILL/守护进程丢失后的自动清理。异常清理需按所有权记录逐个核对资源。
- 没有生产部署、远程推送、main 合并、服务重启、镜像构建或新增运行时依赖。

原有基础模块的验收保持见 `2026-10-26-manager-service-progress.md`，不把之前结果重复计为本次 Docker 隔离通过。
