# Pi Web v1 与独立 Pi Manager 拆分设计

日期：2026-10-26。状态：用户已于本日确认书面设计，已进入独立拆包实施；各能力是否可用以验证记录为准，不因设计获批而视为实现完成。

## 1. 目标与启动顺序

用户需要两个清晰产品：会话交互扩展 Pi Web，以及合并 Hub/Gate 管理能力的 Pi Manager。不能要求先在 Pi 里加载管理器，才能创建第一个 Pi。

```text
独立启动 Pi Manager（此时允许零个 Pi）
    ├─ 人通过管理网页创建/管理 Pi
    ├─ 可选 MCP 客户端提交/查询管理任务
    └─ 受限执行器启动 Pi
           └─ Pi 加载 Web 扩展，提供聊天页面
```

Pi、Web 扩展或 MCP 客户端退出，不得导致管理器退出。更新 Pi 进程时，任务仍由管理器跟踪。

## 2. 采用的拆分方式

选择“独立管理产品 + 薄会话扩展”，不选择“管理器本身作为 Pi 扩展”，也不将目前的 Hub/Gate 简单包装成随 Pi 启停的 MCP 子进程。

用户只需理解一个管理产品、一份管理配置和一个状态根目录。内部仍分离入口与执行器：前者提供网页、会话路由和 MCP；后者仅按冻结策略执行经过授权的动作。两者可以由同一安装/启动入口管理，但不为省一个进程而让公共网页拥有无限 Docker/宿主机执行权。

项目目录为 `pi-manager`，独立版本、独立构建和测试；Web 保留在原仓库的字面分支 `v1`。本轮不更改旧部署和历史分支。

## 3. Pi Web v1 的保留与移出

保留聊天、流式输出、模型与思考等级切换、会话树、恢复/切换会话、编辑/重新生成、数学渲染、图片和文件上传下载，以及已实现的扩展交互面板。`/mcp`、`/agents` 等会话内授权与选择面板不因管理拆分而移除。

保留可选的管理器登记适配：未配置管理器时单会话 Web 正常启动；管理器不可达时不阻塞聊天，不无限重试或积累登记数据；连接恢复时按身份重新登记。适配器仅传递需要的状态，不持有管理员凭据或容器控制接口。

移出 Hub 多会话门户、全局审批、创建 Pi、全局版本更新/回退、执行器与管理服务部署工具。Web 包不再提供 `pi-web-hub` 可执行文件，不再构建或打包 Hub。

同步调整包清单、构建脚本、类型检查范围、`web-dist` 来源清单、安装测试和文档。不能仅删除 `hub/`，留下仍要求 Hub 构建产物的安装校验。

## 4. Manager 职责与共享协议

迁入多会话入口、登记与路由、任务/审批、Pi 生命周期管理、版本目录和更新/回退；纳入扩展安装/更新/移除任务。前端操作和 MCP 调用使用同一任务模型，不各建一套更新逻辑。

Pi 侧保留薄适配器；管理器不通过导入相邻 Web 源码目录获取类型。第一阶段用版本化的协议定义和独立契约夹具建立兼容关系：仓库各自包含可发布的必要定义，用一致性测试发现漂移，不引入未发布的第三个共享包。新增字段保持兼容；不兼容版本明确拒绝并提示升级。

登记包含实例身份、工作目录显示信息、后端类型、版本和能力。显示“看见的实例”不代表“有权控制的实例”：外部启动的原生 Pi 只能在明确接入并获得控制授权后被重启或更新，不能扫描任意 PID 并接管。

## 5. 原生与 Docker 后端

管理器必须不依赖 WSL、用户私有脚本或固定用户名。原生后端通过显式配置的 Pi 安装路径及工作目录启动受管子进程；Docker 后端使用明确允许的镜像、目录、卷和安全参数。后端不支持的功能显示为不可用，不能用 Docker 后端的验收替代原生后端。

第一轮可运行验收包括本机原生后端和 Docker 后端；跨操作系统的启动差异必须单独验证，不能把 Linux/WSL 通过称为 Windows/macOS 已支持。远程连接不内置阿里云依赖：保留现有反向代理兼容能力，但本轮不修改域名、TLS、登录或隧道。

创建目录仅限管理员配置的工作区根目录。拒绝路径穿越、越界符号链接和不允许的挂载。当前个人部署的 gitproject 限制是部署策略，不硬编码进通用产品。

## 6. 任务、审批与更新安全

任务必须有持久化 ID、请求者、目标身份、动作、精确版本/来源、授权范围、状态和结果。重复请求通过幂等键返回原任务。客户端断开不撤销已批准任务，也不自动重复执行结果不明的动作。

建议统一状态：`pending_approval`、`queued`、`waiting_idle`、`running`、`succeeded`、`failed`、`cancelled`、`unknown`。需要等待模型生成结束时保留 `waiting_idle`，新一轮生成与更新激活之间必须有互斥控制，不能只轮询一次“空闲”。

MCP 接口提供查询能力及提交创建/停止、Pi 更新/回退、扩展管理任务的能力。MCP 请求不包含“自行批准”或任意 shell/Docker 参数；审批由独立的人类管理权限或管理员预设的窄自动策略决定。网页登录不自动赋予所有管理动作权限。

候选版本先完成来源/内容校验及隔离兼容性检查，再切换。失败不得提前停止原进程；不兼容的会话回退须在切换前拒绝。共享安装与扩展目录需加锁；多消费者使用同一目录时，必须做分阶段激活或等待所有受影响消费者安全进入切换点，不能边生成边覆写共享依赖。

MCP 的具体 SDK、协议版本、认证及传输选型在实施计划前核对官方文档并冻结。本设计仅确定“连接到独立服务”的职责，不声称已有可用 MCP 服务，也不假定 Pi 已内置可用客户端。

## 7. 配置、状态及迁移

配置只描述监听地址、认证引用、允许根目录、后端和任务策略；凭据文件单独限制权限，不嵌入源码或日志。运行状态集中到显式配置的数据目录（容器可映射为 `/data`），保存登记、任务与审计信息；同一状态目录禁止多个执行器无锁写入。

不把整个宿主机、Docker 根目录或个人 HOME 直接暴露给 Web。需要控制 Docker 的接口仅由受限执行器持有；MCP/聊天端拿不到底层控制凭据。

迁移是显式导入、试运行、验证、切换、保留恢复点的流程。无配置时使用独立的测试/默认新状态，不自动读取真实 `pi-home` 或生产 Gate 数据。迁入旧状态前做 schema 校验与可恢复备份；新旧执行器不得同时管理同一目标。

## 8. 实施阶段与完成标准

1. **建立边界**：完成本设计及 v1 分支/新目录。此阶段不宣称完成源码拆分。
2. **源码拆包**：迁入 Manager 的管理源码、测试及许可；清理 Web 包和构建，两个项目都能独立安装、构建、验证，不引用兄弟目录。
3. **独立管理服务**：零 Pi 启动、持久任务、管理网页和双后端生命周期。先保留现有行为，针对迁移缺口补测试。
4. **MCP 与扩展管理**：冻结接口，接入同一任务队列，实现权限及幂等检查；不以只有工具名称/假响应的骨架作为完成。
5. **隔离验收**：真实原生 Pi 与 Docker Pi、Web 登记与路由、版本切换/回退、扩展管理，以及授权/失败边界测试。使用临时状态、测试凭据和自有资源，不用生产卷。

必须通过的验收场景：

- 零个 Pi 时启动 Manager，并在管理网页创建第一个受管 Pi；Pi 结束后管理网页仍可用。
- 原生与 Docker 各跑一遍创建、登记、停止和恢复；不支持的平台有明确说明。
- 不装 Manager 的 Pi 能独立使用干净 Web；安装 Web 不额外启动管理器。
- MCP 断开/客户端退出后任务可在网页继续查询；无管理授权的 Agent 不能批准自己的申请。
- 更新中等待生成结束、重复提交、服务重启、失败恢复，以及兼容回退；没有宽泛版本硬编码。
- 干净安装和更新后 Web 的模型/树、恢复、编辑重答、公式、图片/文件、扩展授权交互无回归。
- 类型、构建、分发完整性、单元与契约测试；网页变化另做桌面/手机实际截图检查。受限环境未跑的测试明确列出，不能用旧项目结果冒充。

## 9. 本轮交付边界与审阅

建立 `v1` 工作分支、新项目文档和来源记录之后，用户已确认书面设计；本轮按独立拆包计划实施第 2 阶段并记录验收。仍不推送、不合并 main、不安装替换已用扩展、不重启服务。阶段 3–5 的服务整合、双后端、MCP 和扩展管理须继续按各自计划实现，不因本轮拆包而视为完成。管理器命令名和包元数据以实际构建产物为准；此设计不提供未经验证的安装命令。

自审结果：两个产品的职责、零 Pi 启动、MCP 权限、原生/Docker 验收和回滚边界已明确；来源快照与未迁移状态分开记录。没有将“新目录/新分支”标记为可部署成果。
